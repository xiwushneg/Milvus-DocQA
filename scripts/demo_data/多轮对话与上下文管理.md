# 多轮对话与上下文管理

## 多轮对话给 RAG 带来的新问题

单轮问答中，用户的问题是自包含的。多轮对话则充满口语化的省略与指代："那第二种呢？""它的部署方式呢？"——这类问题直接送进检索会彻底失效，因为"第二种""它"脱离对话历史毫无意义。因此多轮 RAG 在检索之前多了一个必经环节：把带指代的用户问题改写成自包含的独立查询。

## 查询改写

查询改写通常用一次轻量的大模型调用完成：把对话历史与最新问题一起交给模型，输出一个消解了指代、补全了上下文的独立问题。例如历史中讨论过 Milvus 的索引，用户追问"那它需要多少内存"，改写后就变成"Milvus 的 HNSW 索引需要多少内存"。这次额外调用增加少量延迟，但决定了检索是否命中，是值回票价的投资。

## 对话历史的裁剪

对话历史不能无限增长，否则提示词膨胀、成本上升且关键信息被稀释。常见策略有三：滑动窗口只保留最近 N 轮；历史摘要，把较早的对话压缩成一段摘要放入提示词；混合策略，最近几轮保留原文、更早内容摘要化。对知识库问答，还应识别话题切换：用户换了新话题后，旧话题的历史对改写反而形成干扰，应及时截断。

## 会话级引用一致性

多轮场景下引用要跟随会话维护：同一轮答案的 [1][2] 指向本轮检索到的片段，跨轮追问时要重新检索并重新编号，避免引用错乱。实现上每轮请求独立检索、独立编号，前端按轮次渲染引用，保证任何一轮的引用都能在本轮的来源列表中闭环。
